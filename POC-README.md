# PoC: Optimal (GPT-5.6-sol) Retriever for Memory-Split

**Question.** At a fixed parameter budget, does a language model that *offloads
facts* to an external retriever (SPLIT) beat a dense twin that stores everything
in its weights (DENSE) — once retrieval is no longer the bottleneck?

This PoC answers the second half by **assuming an optimal retriever**: at eval
time the retrieved value for each question is generated by **GPT-5.6-sol**
(`openai-group/gpt-5.6-sol`) through the TrueFoundry OpenAI-compatible gateway.
Because the facts are **real Wikidata triples** (PopQA), a frontier model
genuinely knows the answers, so the oracle is legitimately near-optimal — and we
report GPT's agreement with the PopQA gold ("fidelity") so the claim is honest.

It is **single-hop** (one lookup per question) and matched: the two arms share
one corpus, the same model, the same token/step budget, and the same
initialization — **the only difference is whether fact values carry training
loss** (DENSE) or are masked out (SPLIT, LMLM-style).

**Scale.** Defaults to the team's primary science scale **`d160m` (~162M
params)**; `--model d360m` (~356M) matches the stretch scale (needs an A100),
`--model toy` (~29M) is the cheap pilot. Architecture and per-scale
`micro_batch_size` / `lr` mirror `train/model.py` PRESETS and
`scripts/make_relational_manifest.py`.

## How it works

- **Corpus** (`corpusgen/poc_build.py`): real PopQA facts as `Question /
  Reasoning / Answer` traces (the fact dose) + knowledge-free iGSM/deduction
  (the reasoning composite) + a small English bed. Rendered twice: DENSE inlines
  each fact value; SPLIT wraps it as `<|db_start|>{subj}, {prop}<|db_retrieve|>
  {value}<|db_end|>` with the value loss-masked.
- **Optimal retriever** (`evals/gpt_oracle.py`): `GatewayClient` calls
  GPT-5.6-sol once per eval item; `GPTOracle` returns that item's golden value
  for *any* emitted key (removing the address-construction confound). The
  existing decoder `evals/generate.py` injects the value as the answer text — no
  core change.
- **Eval** (`evals/oracle_scorer.py`): SPLIT decodes with the per-item oracle;
  DENSE decodes closed-book. Both scored by `evals/keyguess.py` (alias-tolerant
  answer match), grouped **seen vs held-out**.
- **Orchestration** (`scripts/poc_run.py`): `build → train → gen-golden → eval →
  report`.

## Run it (Colab)

Open `notebooks/poc_optimal_retriever.ipynb` on a GPU runtime and run top to
bottom. You'll paste a TrueFoundry token when prompted. It clones this branch,
builds the corpus (offline; facts are committed), trains both twins, generates
golden knowledge, evaluates, and renders the results figure.

## Checkpoints & Google Drive (Colab)

Colab runtimes are ephemeral — a disconnect wipes the local disk. Set
`POC_PERSIST_DIR` to a mounted Drive folder and the **checkpoints, the (paid)
GPT golden cache, results, and figure** are written there; the **corpus stays
local** (fast memmap reads) and is rebuilt byte-identically from the same seeds.
The notebook's "Persist to Google Drive" cell does this for you.

After a disconnect: re-run clone + install + the Drive cell, then `--stage build`
(fast, deterministic), then `--stage train` — it **auto-resumes** from the last
Drive checkpoint (`--ckpt-minutes` controls save cadence; a final ckpt always
saves at the end; `--fresh` restarts). Without `POC_PERSIST_DIR`, everything
lands under the ephemeral local `data/poc/`.

## Run it (local)

```bash
uv venv .venv --python 3.12
uv pip install -r requirements.txt --python .venv/bin/python
export PYTHONPATH=.
cp .env.example .env    # fill in OPENAI_API_KEY (your TrueFoundry token)

.venv/bin/python scripts/poc_run.py --stage build
.venv/bin/python scripts/poc_run.py --stage train          # CPU/MPS ok, slow
set -a && . ./.env && set +a
.venv/bin/python scripts/poc_run.py --stage gen-golden
.venv/bin/python scripts/poc_run.py --stage eval --gold-oracle
.venv/bin/python scripts/poc_run.py --stage report
```

Offline wiring tests (no network, no creds):

```bash
.venv/bin/python -m pytest tests/test_poc.py -q
```

## Knobs (`scripts/poc_run.py`)

`--model {toy,d160m,d360m}` (scale; default d160m), `--steps` (train steps),
`--max-facts` (cap PopQA facts), `--exposures`,
`--igsm-docs/--deduction-docs/--bed-docs`, `--heldout/--seen` (fact-QA eval
sizes; default 25 + 25 = 50), `--gold-oracle` (also report the exact upper
bound with PopQA gold injected), `--ground-truth-fallback` (inject gold when
GPT disagrees, making the oracle exactly optimal), `--gpt-model`.

## Reading the results

- **Held-out fact-QA:** SPLIT@GPT-oracle should ≫ DENSE@closed-book. Note this
  gap is *partly definitional* — the dense arm never saw those facts — so it
  demonstrates the freshness/externalization benefit, not capacity alone.
- **Seen fact-QA:** the fairer capacity comparison — both arms trained on these
  facts; SPLIT should be ≥ DENSE (retrieval is lossless; parametric recall loses
  the long tail).
- **Reasoning composite (iGSM + deduction):** the direct capacity-crowding
  signal. Even at d160m this runs on **far fewer tokens than the team's cluster
  runs** (a single Colab GPU overnight, not billions of tokens), so treat it as
  indicative/supporting, not a final measurement.
- **GPT fidelity:** how optimal GPT-5.6-sol actually was vs the PopQA gold.

This measures the **upper bound** of the split approach (perfect retrieval); the
real retriever the team is building will land below it.
